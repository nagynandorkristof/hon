# hOn Integration — Reliability & Robustness Audit

**Date:** 2026-08-17 (extended same day to cover the vendored `pyhon` library)
**Scope:** Part 1 covers `custom_components/hon/` (the HA integration layer). Part 2 extends the same aspects to `custom_components/hon/pyhon/` — the `pyhOn` cloud client library, originally an external pip dependency pinned at `0.17.5`, now vendored directly into this repo (see the vendoring change earlier in this session) so it can be inspected and fixed in place rather than treated as a black box.
**Method:** Manual read-through of every module plus targeted `grep` verification of each claim below. All file:line references point at the code as of commit `70eb6c0` plus the in-progress vendoring changes in the working tree.

## TL;DR

**Part 1 (integration layer):** reasonable architecture (push-based `DataUpdateCoordinator`, per-appliance entity descriptions), but has **zero exception handling anywhere in the integration code** — not one `try`/`except` block exists in the whole `custom_components/hon/` tree (excluding the vendored library). Combined with several entity types that never implement HA's `available` property, this means: any hiccup in the cloud API (auth expiry, timeout, malformed payload, missing dict key) either crashes setup, spams the log on every push update, or silently leaves entities reporting stale data as if everything were fine. This is not theoretical — a production log confirms an ordinary DNS timeout while calling the hOn cloud API crashes `climate.set_temperature` with a raw, unhandled traceback (see [4.1](#41-confirmed-in-the-wild-unhandled-clientconnectordnserror-crashes-climateset_temperature--critical)).

**Part 2 (vendored `pyhon` library):** better than the integration layer — it does have a real exception taxonomy and does catch some things — but has three serious gaps of its own: **no timeout is ever set on any HTTP request** (so a hung cloud connection can block for aiohttp's default 5 minutes, which is exactly what the production traceback in 4.1 was waiting on before it failed); the one place that sends a command to a device (`HonCommand.send_parameters`) only catches `NoAuthenticationException`, letting every network error and its own `ApiError` propagate unhandled — this is the precise root cause of 4.1, now pinpointed to [`commands.py:148-162`](../custom_components/hon/pyhon/commands.py#L148-L162); and the **MQTT reconnect watchdog has no self-protection** — if a reconnect attempt itself throws, the watchdog task dies silently and push updates stop forever until a full integration reload, undermining the entire "no polling needed, we use push" architecture. There is also a working, unused safety net: `HonAppliance.update()` implements exactly the periodic-refresh fallback Part 1's finding 2.1 says is missing, complete with a 5-second debounce — but nothing in the codebase ever calls it. Separately, the device-identification constants sent on every request (`OS_VERSION = 999`, `USER_AGENT = "Chrome/999.999.999.999"`, `DEVICE_MODEL = "pyhOn"`) are implausible placeholder values rather than a real device fingerprint — a reliability risk if Haier ever validates them server-side, and notable given this repo's documented takedown history (see [12](#12-deviceclient-identification-constants-sent-to-the-hon-cloud--high-reliability-and-worth-noting-given-this-repos-history)).

None of this is covered by tests — there is no test suite in the repository at all, for either the integration or the vendored library.

# Part 1: HA integration layer (`custom_components/hon/*.py`)

## 1. Production readiness

### 1.1 No exception handling anywhere — Critical
```
$ grep -rn "except" custom_components/hon
(no results)
```
Every single I/O boundary — cloud login, command sends, coordinator push callbacks — is unguarded. In a normal HA integration this is usually masked because HA's core wraps service calls and config entry setup in its own try/except, so failures surface as a UI error/log traceback rather than crashing the whole system. But it means:
- No integration-specific error messages (the user sees a raw `pyhOn` exception/traceback, not "wrong password" or "device unreachable").
- No retry/backoff — a single transient network blip surfaces as a hard failure with no recovery path other than a manual reload.
- No distinction between "credentials are wrong" (needs reauth) and "cloud is temporarily down" (should retry).

### 1.2 `async_setup_entry` doesn't use HA's readiness/retry contract — High
[`__init__.py:30-46`](../custom_components/hon/__init__.py#L30-L46)
```python
async def async_setup_entry(hass: HomeAssistantType, entry: ConfigEntry) -> bool:
    ...
    hon = await Hon(
        email=entry.data[CONF_EMAIL],
        password=entry.data[CONF_PASSWORD],
        ...
    ).create()
```
If `Hon(...).create()` raises (network down, hOn API down, expired/invalid refresh token, wrong password), the exception propagates uncaught. HA's convention for this exact situation is to catch connection/auth errors and re-raise as `ConfigEntryNotReady` (triggers automatic retry with backoff) or `ConfigEntryAuthFailed` (triggers the reauth flow, prompting the user to re-enter credentials). Neither is used here, so:
- A transiently-unreachable cloud API permanently fails the config entry instead of HA auto-retrying.
- An expired/revoked refresh token or changed password has no reauth UX — the entry just breaks silently until the user manually deletes and re-adds it.

**Suggested fix:**
```python
from homeassistant.exceptions import ConfigEntryNotReady, ConfigEntryAuthFailed
from pyhon.exceptions import HonAuthenticationError  # or whatever pyhOn exposes

try:
    hon = await Hon(...).create()
except HonAuthenticationError as err:
    raise ConfigEntryAuthFailed from err
except (TimeoutError, aiohttp.ClientError) as err:
    raise ConfigEntryNotReady from err
```

### 1.3 Deprecated, fire-and-forget platform forwarding — Medium
[`__init__.py:56-59`](../custom_components/hon/__init__.py#L56-L59)
```python
for platform in PLATFORMS:
    hass.async_create_task(
        hass.config_entries.async_forward_entry_setup(entry, platform)
    )
```
`async_forward_entry_setup` (singular) has been deprecated in Home Assistant core in favor of `hass.config_entries.async_forward_entry_setups(entry, PLATFORMS)` (plural, batched). Wrapping each call in a detached `async_create_task` also means setup errors in individual platforms are never awaited or surfaced to `async_setup_entry` — they just log a warning from the event loop's default task-exception handler and the config entry still reports as loaded successfully.

**Suggested fix:**
```python
await hass.config_entries.async_forward_entry_setups(entry, PLATFORMS)
```

### 1.4 `async_unload_entry` unguarded dict access — Medium
[`__init__.py:63-64`](../custom_components/hon/__init__.py#L63-L64)
```python
async def async_unload_entry(hass: HomeAssistantType, entry: ConfigEntry) -> bool:
    refresh_token = hass.data[DOMAIN][entry.unique_id]["hon"].api.auth.refresh_token
```
If setup failed partway (e.g. raised before `hass.data[DOMAIN][entry.unique_id]` was populated at [`__init__.py:53-54`](../custom_components/hon/__init__.py#L53-L54)), HA still calls `async_unload_entry` during cleanup/retry, which will `KeyError` here instead of unloading gracefully.

**Suggested fix:** guard with `.get()` and bail out early if the entry was never fully set up.

## 2. Polling / coordinator pattern

The integration is declared `"iot_class": "cloud_push"` in [manifest.json](../custom_components/hon/manifest.json) and correctly uses a shared `DataUpdateCoordinator` per config entry ([`__init__.py:48-51`](../custom_components/hon/__init__.py#L48-L51)):
```python
coordinator: DataUpdateCoordinator[dict[str, Any]] = DataUpdateCoordinator(hass, _LOGGER, name=DOMAIN)
hon.subscribe_updates(coordinator.async_set_updated_data)
```
No `update_interval` or `update_method` is passed, so this coordinator **never polls** — it is used purely as a pub/sub broadcast bus that `pyhOn` pushes into. This is a defensible pattern for a push-based API, but it has a specific consequence worth flagging:

### 2.1 No fallback polling / staleness detection — High
Because `update_interval` is unset, `DataUpdateCoordinator._async_update_data` is never invoked, so `coordinator.last_update_success` never changes from its initial `True` — it is not wired to real connectivity at all. If `pyhOn`'s underlying push channel (MQTT / long-poll, whatever it uses internally) silently disconnects and never reconnects, **nothing in this integration will ever notice**. There is no periodic re-sync, no heartbeat, no "haven't heard from the device in N minutes, mark unavailable" logic.

The mitigation that exists is per-entity: several entity classes independently check `self._device.connection` and/or `attributes.lastConnEvent.category` in their own `available` property. But this is inconsistent — see 2.2.

**Suggested fix:** Either (a) have `pyhOn`/the integration set a fallback `update_interval` — **no less frequent than once per minute**, driven by a single named constant rather than a hardcoded literal so it's easy to tune per findings 8.2/17 below — as a full-refresh in addition to push updates, so a dead push connection self-heals, or at minimum (b) track the last-seen push timestamp and flip `coordinator.last_update_success = False` (via `async_set_update_error`) if no update has arrived within some multiple of that same constant.

### 2.2 Inconsistent `available` implementation — High
```
$ grep -n "def available" custom_components/hon/*.py
button.py, fan.py, select.py, lock.py, light.py, number.py, switch.py
```
`sensor.py`, `binary_sensor.py`, and `climate.py` **never override `available`**. They inherit the base `CoordinatorEntity.available`, which just reflects `coordinator.last_update_success` — and per 2.1, that flag never goes false in this integration's push-only setup. Practically: **every sensor, binary sensor, and climate entity will show as "available" in Home Assistant forever, even when the physical appliance has been offline for days**, while switches/numbers/selects/locks on the same device correctly go unavailable via their explicit `self._device.connection` / `remoteCtrValid` checks (e.g. [`switch.py:504-511`](../custom_components/hon/switch.py#L504-L511), [`number.py:274-280`](../custom_components/hon/number.py#L274-L280)).

This is user-visible and easy to hit: a washing machine sensor showing "Program: Cotton 40°" from three days ago, with no indication the reading is stale, while the switch for the same machine correctly shows unavailable.

**Suggested fix:** Add a shared `available` implementation in the base `HonEntity` class ([`entity.py`](../custom_components/hon/entity.py)) that checks `self._device.connection` (or the connectivity attribute) by default, and have subclasses opt out only where genuinely not applicable, rather than each subclass opting in individually.

## 3. Error handling around cloud payloads

Given finding 1.1 (no `except` blocks at all), every place below is a raw crash point, not a "narrow except" issue.

### 3.1 Unhandled `KeyError` on lookup-table misses in `climate.py` — High
[`climate.py:196`](../custom_components/hon/climate.py#L196) and [`climate.py:251`](../custom_components/hon/climate.py#L251):
```python
return HON_HVAC_MODE[self._device.get("machMode")]
...
return HON_FAN[self._device.get("windSpeed")]
```
`HON_HVAC_MODE` ([`const.py:45-53`](../custom_components/hon/const.py#L45-L53)) only defines keys `0-6`, and `HON_FAN` ([`const.py:63-69`](../custom_components/hon/const.py#L63-L69)) only defines `1-5`. If the cloud API ever reports a `machMode`/`windSpeed` value outside those ranges (new firmware, new appliance variant, transient bad payload), this raises `KeyError` from inside a `@property` getter that Home Assistant polls on every state write — i.e. the climate entity becomes permanently broken (repeated tracebacks in the log) until the value changes back or the integration is reloaded.

**Suggested fix:** `HON_HVAC_MODE.get(mode, HVACMode.OFF)` / `HON_FAN.get(speed, FAN_AUTO)` with a documented fallback, and log a warning so an unmapped value is discoverable instead of crashing.

### 3.2 Unhandled `raise ValueError` inside a coordinator push callback — Medium
[`sensor.py:838-840`](../custom_components/hon/sensor.py#L838-L840):
```python
if self.entity_description.key == "programName":
    if not (options := self._device.settings.get("startProgram.program")):
        raise ValueError
```
This runs inside `_handle_coordinator_update`, which fires on *every* push update for the lifetime of the entity. If `startProgram.program` is ever momentarily absent from the settings payload (e.g. mid-program-change, or a partial API response), this isn't a one-off failure — it raises on every subsequent update until the missing key reappears, spamming the log and leaving the "Program Name" sensor's state stuck.

Similarly, `_set_temperature_bound` in `climate.py` ([`climate.py:166-169`](../custom_components/hon/climate.py#L166-L169) and [`climate.py:415-418`](../custom_components/hon/climate.py#L415-L418)) does `raise ValueError` if a setting isn't a `HonParameterRange`, called both from `__init__` (would fail entity creation entirely) and from `async_set_preset_mode` (would fail mid-command).

**Suggested fix:** Treat a missing/malformed setting as "no data yet" (skip the update, keep previous state, log at debug level) rather than raising, unless the intent really is to prevent entity creation — in which case catch it at the `async_setup_entry` call site so one malformed appliance doesn't break the whole platform's `async_add_entities` batch.

### 3.3 No validation of config data before appliance-type dispatch — Low
Every platform's `async_setup_entry` (e.g. [`switch.py:410-411`](../custom_components/hon/switch.py#L410-L411), [`sensor.py:815-816`](../custom_components/hon/sensor.py#L815-L816)) does:
```python
for device in hass.data[DOMAIN][entry.unique_id]["hon"].appliances:
    for description in SWITCHES.get(device.appliance_type, []):
```
This part is actually fine — unknown `appliance_type` values degrade gracefully to an empty tuple via `.get(..., [])`. Flagging only because it's the *one* place defensive coding is present, which highlights by contrast how little exists elsewhere (e.g., 3.1/3.2 use direct `[]` / no default).

### 4.1 Confirmed in the wild: unhandled `ClientConnectorDNSError` crashes `climate.set_temperature` — Critical

A user-supplied Home Assistant log shows finding H (and the root cause, finding 1.1) actually occurring in production, not just as a theoretical code-path risk:

```
aiodns.error.DNSError: (12, 'Timeout while contacting DNS servers')
...
OSError: [Errno None] Timeout while contacting DNS servers
...
File "/config/custom_components/hon/climate.py", line 198, in async_set_temperature
    await self._device.commands["settings"].send()
File "/usr/local/lib/python3.13/site-packages/pyhon/commands.py", line 133, in send
    return await self.send_parameters(params)
...
File "/usr/local/lib/python3.13/site-packages/pyhon/connection/api.py", line 236, in send_command
    async with self._hon.post(url, json=data) as response:
...
aiohttp.client_exceptions.ClientConnectorDNSError: Cannot connect to host api-iot.he.services:443 ssl:default [Timeout while contacting DNS servers]
```

**What happened:** the user called the `climate.set_temperature` service on an AC entity (`HonACClimateEntity.async_set_temperature`, [`climate.py:184-189`](../custom_components/hon/climate.py#L184-L189)). DNS resolution for `api-iot.he.services` timed out — a transient, entirely expected condition for anything talking to a cloud API (DNS hiccup, brief outage, container network blip on HA restart) — and `pyhOn` raised `aiohttp.client_exceptions.ClientConnectorDNSError`. Because neither `pyhOn`'s `send_command`/`send`/`send_parameters` call chain nor `climate.py`'s `async_set_temperature` catches anything (per 1.1), the exception propagates unmodified through `HonACClimateEntity.async_set_temperature` → HA's `entity_service_call`/`async_service_temperature_set` → the websocket API handler, which is the only thing that ends up catching it — turning what should be a clean, actionable integration error into a raw traceback surfaced to whatever called the service (frontend UI toast or automation log), with no indication of "hOn cloud unreachable, will retry" and no retry actually happening.

This is the single clearest piece of evidence that finding 1.1 (no exception handling anywhere) is not just a theoretical robustness gap — it directly degrades the everyday user experience for one of the most common actions in this integration (setting a temperature), on nothing more than an ordinary transient network condition.

**Suggested fix:** wrap all `await self._device.commands[...].send()` call sites (there are 6, at [`climate.py:188,212,259,287,356`](../custom_components/hon/climate.py#L188) and equivalents in `switch.py`, `number.py`, `select.py`, `lock.py`, `fan.py`, `light.py`, `button.py`) in a shared helper, e.g.:
```python
async def _send_command(command) -> None:
    try:
        await command.send()
    except (aiohttp.ClientError, TimeoutError) as err:
        raise HomeAssistantError(
            f"Could not reach hOn cloud: {err}"
        ) from err
```
`HomeAssistantError` is the correct exception type for a service-call failure — HA surfaces it to the user as a clean, readable message ("Could not reach hOn cloud: ...") instead of a full Python traceback, and it does not require every call site to hand-roll its own try/except.

## 5. Robustness against malformed/partial API data

- **Dict/attribute access is pervasive and mostly unguarded.** Patterns like `self._device.settings[self.entity_description.key]` (no `.get`) appear throughout `climate.py`, `switch.py` (`HonConfigSwitchEntity`), `number.py`. If a setting a description references isn't present in `available_settings` for a given firmware/model variant that wasn't accounted for when the entity was created (e.g. it disappears after a firmware update), these raise `KeyError` on every subsequent read. Where `.get()` is used (e.g. `select.py`), it's markedly more resilient — this inconsistency should be resolved in favor of `.get()`+fallback everywhere state getters run on a hot path (properties HA reads on every update).
- **`config_flow.py` does no credential validation at all.** [`config_flow.py:33-54`](../custom_components/hon/config_flow.py#L33-L54) accepts any email/password pair, checks only for a duplicate `unique_id`, and creates the entry unconditionally — it never actually attempts to log in to hOn during the flow. A wrong password is only discovered later during `async_setup_entry` (which, per 1.1/1.2, has no graceful failure path either), giving the user a confusing generic error in the integrations page instead of "incorrect email or password" on the config form itself.
  **Suggested fix:** in `async_step_user`, attempt `await Hon(email, password, ...).create()` (or at least a login-only pyhOn call) before `async_create_entry`, and turn an auth failure into a form error (`errors["base"] = "invalid_auth"`).
- **No reauth flow (`async_step_reauth`)** exists at all, compounding 1.2 — once a refresh token is invalidated by hOn (password change, revoked session, long absence), there is no supported path back to a working state except delete-and-recreate the integration.

## 6. Dependency / test coverage risk

- `pyhOn` is pinned to an exact version, `0.17.5` ([manifest.json](../custom_components/hon/manifest.json), [requirements.txt](../requirements.txt)) with no version range — any upstream bugfix requires a manual bump, but this at least protects against surprise breaking changes from auto-upgrades.
- **There is no test suite anywhere in this repository** (`find . -iname "test*"` returns nothing under `custom_components/`). None of the bugs identified above (KeyError on unmapped enum values, missing `available`, unguarded dict access) would be caught by CI before reaching users — they'd only surface as GitHub issues from real users hitting real edge-case payloads.

# Part 2: Vendored `pyhon` library (`custom_components/hon/pyhon/*.py`)

Unlike Part 1, this code does have a real exception taxonomy ([`exceptions.py`](../custom_components/hon/pyhon/exceptions.py): `HonAuthenticationError`, `NoAuthenticationException`, `NoSessionException`, `HonNoAuthenticationNeeded`, `ApiError`) and 13 `try`/`except` blocks handling specific, deliberate cases (auth retry, JSON decode errors, test-data file loading). The design is more careful overall. But the gaps that remain are the ones that matter most for reliability: no request ever times out, the one path that sends a command to a device only catches one of the several exception types it can actually raise, and the push-update reconnect loop can die permanently and silently.

## 7. Production readiness

### 7.1 No timeout on any HTTP request — Critical
```
$ grep -rn "ClientTimeout\|timeout=" custom_components/hon/pyhon
(no results)
```
[`connection/handler/base.py:46`](../custom_components/hon/pyhon/connection/handler/base.py#L46) creates the shared `aiohttp.ClientSession()` with no `timeout=` argument, and none of the ~15 call sites across [`connection/api.py`](../custom_components/hon/pyhon/connection/api.py) or [`connection/auth.py`](../custom_components/hon/pyhon/connection/auth.py) pass a per-request timeout either. aiohttp's default `ClientTimeout` is a 300-second (5 minute) total timeout. In practice this means: if the hOn cloud API is slow, half-broken, or a DNS/TCP-level connection hangs (rather than failing fast, as in the DNS-timeout traceback in Part 1's finding 4.1 — that one *did* fail relatively fast because DNS resolution itself timed out quickly; a hung TCP connection would not), a single `climate.set_temperature`, sensor refresh, or login attempt can block the calling coroutine — and therefore the Home Assistant service call or config entry setup that triggered it — for up to 5 minutes with no feedback to the user.

**Suggested fix:** set a conservative `aiohttp.ClientTimeout(total=30)` (or similar) when constructing the shared `ClientSession` in `ConnectionHandler.create()` ([`connection/handler/base.py:44-47`](../custom_components/hon/pyhon/connection/handler/base.py#L44-L47)), so failures surface in seconds rather than minutes.

### 7.2 `send_parameters` only catches one of several exceptions it can raise — Critical, confirmed root cause of Part 1 finding 4.1
[`commands.py:142-162`](../custom_components/hon/pyhon/commands.py#L142-L162):
```python
async def send_parameters(self, params: Dict[str, str | float]) -> bool:
    ...
    try:
        result = await self.api.send_command(...)
        if not result:
            _LOGGER.error(result)
            raise ApiError("Can't send command")
    except NoAuthenticationException:
        _LOGGER.error("No Authentication")
        return False
    return result
```
This is the exact call chain behind the production traceback quoted in Part 1's finding 4.1: `climate.py` → `HonCommand.send()` → `send_parameters()` → `self.api.send_command(...)` → `aiohttp`. The `except` clause here catches only `NoAuthenticationException`. Two other failure modes fall straight through unhandled:
1. **Any network-level exception** (`aiohttp.ClientError`, `TimeoutError`, DNS errors like the one observed in production) raised inside `self.api.send_command(...)` — this is precisely what happened in the confirmed production crash.
2. **`ApiError("Can't send command")`**, raised by this very function two lines above the `except` — if the cloud API responds but reports failure (`resultCode != "0"`), this method raises its own exception that it doesn't catch, so callers must catch `ApiError` themselves (none currently do, per Part 1 finding 1.1).

**Suggested fix:** catch `(aiohttp.ClientError, TimeoutError)` here (or, better, wrap them at the `ConnectionHandler` layer into a dedicated `HonConnectionError` per 7.3 below, and catch that), log/raise a clear, typed error, and document that callers (i.e. the HA integration) are expected to catch it — which ties directly into Part 1's fix #0.

### 7.3 No dedicated exception type for connectivity failures — Medium
The exception taxonomy in [`exceptions.py`](../custom_components/hon/pyhon/exceptions.py) covers authentication and session-state problems but has nothing for "the network request itself failed." Callers who want to distinguish "hOn cloud is unreachable, maybe retry" from "credentials are wrong, need reauth" (exactly the distinction Part 1's finding 1.2 asks the HA integration to make) currently have no library-level exception to catch for the first case — they'd have to catch raw `aiohttp.ClientError`/`TimeoutError`, which isn't documented or guaranteed as part of this library's public contract.

**Suggested fix:** introduce `class HonConnectionError(Exception)` in `exceptions.py`, and have `ConnectionHandler._intercept`/`HonConnectionHandler._intercept` catch `aiohttp.ClientError`/`TimeoutError` at the point of the actual request and re-raise as `HonConnectionError`. This gives every caller (including the HA integration) one clean exception to catch for "cloud unreachable," directly enabling Part 1 fix #0 and #1.

## 8. Polling / push-update reliability

### 8.1 MQTT reconnect watchdog has no self-protection — Critical
[`connection/mqtt.py:136-146`](../custom_components/hon/pyhon/connection/mqtt.py#L136-L146):
```python
async def start_watchdog(self) -> None:
    if not self._watchdog_task or self._watchdog_task.done():
        self._watchdog_task = asyncio.create_task(self._watchdog())

async def _watchdog(self) -> None:
    while True:
        await asyncio.sleep(5)
        if not self._connection:
            _LOGGER.info("Restart mqtt connection")
            await self._start()
            self._subscribe_appliances()
```
This is the actual mechanism behind the "push, not poll" architecture: a 5-second watchdog loop that notices a dropped MQTT connection and reconnects. It is a good design — but `_start()` ([`connection/mqtt.py:108-123`](../custom_components/hon/pyhon/connection/mqtt.py#L108-L123)) calls `await self._api.load_aws_token()` (a network request, itself unguarded per 7.1/7.2) and `mqtt5_client_builder.websockets_with_custom_authorizer(...)`, either of which can raise. Since `_watchdog()` has no `try`/`except` around its body, **any exception during a reconnect attempt kills the `asyncio.Task` outright**. `asyncio.create_task` fire-and-forget tasks that raise are not retried or restarted by anything — the task simply ends, logged only via asyncio's default "Task exception was never retrieved" warning (easy to miss in HA's logs). From that point on, `self._connection` may remain `False` forever, but nothing will ever call `_start()` again: **live updates stop permanently** until the entire integration is reloaded (e.g. HA restart or manual reload), silently defeating the fallback that finding 8.1 exists to provide.

Combined with Part 1's finding 2.1/2.2 (no HA-side staleness detection, and `sensor`/`binary_sensor`/`climate` entities never check `available`), this means a single transient failure during a reconnect (a DNS blip, an expired AWS token, a brief hOn outage) can silently and permanently freeze all sensor/climate state for a device, with zero visible indication to the user beyond a single easy-to-miss log line at `asyncio` level.

**Suggested fix:**
```python
async def _watchdog(self) -> None:
    while True:
        await asyncio.sleep(5)
        if not self._connection:
            try:
                _LOGGER.info("Restart mqtt connection")
                await self._start()
                self._subscribe_appliances()
            except Exception:
                _LOGGER.exception("MQTT reconnect failed, will retry")
```
so a failed reconnect attempt is logged and retried on the next tick instead of ending the loop forever.

### 8.2 A working periodic-refresh fallback exists but is never called — High
[`appliance.py:28,213-219`](../custom_components/hon/pyhon/appliance.py#L213-L219):
```python
class HonAppliance:
    _MINIMAL_UPDATE_INTERVAL = 5  # seconds
    ...
    async def update(self, force: bool = False) -> None:
        now = datetime.now()
        min_age = now - timedelta(seconds=self._MINIMAL_UPDATE_INTERVAL)
        if force or not self._last_update or self._last_update < min_age:
            self._last_update = now
            await self.load_attributes()
            self.sync_params_to_command("settings")
```
This method exists specifically to do a debounced REST re-fetch of an appliance's attributes — exactly the periodic fallback poll that Part 1's finding 2.1 recommends adding as a safety net against a dead push connection. It's already written, debounced, and ready to use.

```
$ grep -rn "\.update(" custom_components/hon --include=*.py | grep -v "dict update\|attributes\[.parameters.\]"
(no call site outside its own definition)
```
**Nothing in this repository — neither the vendored library nor the HA integration — ever calls `appliance.update()`.** The integration relies entirely on MQTT push via `hon.subscribe_updates(coordinator.async_set_updated_data)` ([`__init__.py:51`](../custom_components/hon/__init__.py#L51)); there is no periodic timer anywhere that also calls this method as a belt-and-suspenders re-sync.

**Suggested fix:** in `custom_components/hon/__init__.py` (or `coordinator.py` once extracted, per Part 3 §15/17), register `coordinator.update_interval` with an `_async_update_data` that iterates `hon.appliances` calling `await appliance.update()`, so a silently-dead MQTT connection (8.1) is self-healed by an independent periodic REST refresh rather than requiring the user to notice and manually reload the integration.

**The interval must be no less frequent than once per minute, and must be a single named constant, not a hardcoded literal.** This is a fallback safety net for a push-based integration, not the primary update path — if it's set too loosely (e.g. the "5–15 minutes" figure this document originally floated in 2.1), a dead MQTT connection can leave every entity showing data that's stale by that same margin before the fallback even fires once, which defeats the purpose of calling this a *reliability* fix. Define it once, e.g. in `const.py`:
```python
FALLBACK_POLL_INTERVAL = timedelta(minutes=1)  # must not be looser than this
```
and reference `FALLBACK_POLL_INTERVAL` from wherever `coordinator.update_interval` is set, rather than writing the duration inline. A single named constant also makes this the one place to tune the tradeoff between staleness-detection latency and unnecessary REST load on the hOn API if real-world testing shows 1 minute is too aggressive for some account sizes — the debounce already inside `HonAppliance.update()` itself (`_MINIMAL_UPDATE_INTERVAL = 5` seconds, appliance.py:28) is a separate, unrelated guard against calling it more than once every 5 seconds per appliance and does not substitute for the coordinator-level constant.

## 9. Error handling around cloud/MQTT payloads

### 9.1 Unguarded lookups in the MQTT message callback — High
[`connection/mqtt.py:79-106`](../custom_components/hon/pyhon/connection/mqtt.py#L79-L106):
```python
def _on_publish_received(self, data: mqtt5.PublishReceivedData) -> None:
    if not (data and data.publish_packet and data.publish_packet.payload):
        return
    payload = json.loads(data.publish_packet.payload.decode())
    topic = data.publish_packet.topic
    appliance = next(
        a for a in self._appliances if topic in a.info["topics"]["subscribe"]
    )
    ...
```
Three unguarded failure points in the hot path that runs on every single push message from every device:
1. `json.loads(...)` — a malformed/partial payload raises `json.JSONDecodeError` uncaught.
2. `a.info["topics"]["subscribe"]` — plain dict indexing; raises `KeyError` if an appliance's `info` is missing the `"topics"` or `"subscribe"` key (plausible for a partially-loaded appliance, see 10.1).
3. `next(a for a in self._appliances if ...)` — has no default, so if the topic doesn't match any currently-known appliance (a real possibility: HA reloading mid-message, an appliance added on the hOn account after startup, or the failure mode in 9.2 below), this raises `StopIteration`.

This callback is invoked directly by the `awscrt`/`awsiot` native MQTT client on message receipt (not on the asyncio event loop in the usual sense — it's a callback registered with `on_publish_received=self._on_publish_received` in `_start()`). An unhandled exception here has a worse failure mode than a normal asyncio callback: depending on how the underlying C extension's callback dispatch handles Python exceptions, this can silently drop just this one message, spam stderr, or in the worst case destabilize the native client's callback thread — none of which is visible from Home Assistant's own logs in an obvious way.

**Suggested fix:** wrap the body of `_on_publish_received` in a `try/except Exception: _LOGGER.exception(...)` so a single malformed message is logged and dropped instead of risking the native client's callback path, and use `next(..., None)` with an explicit `if appliance is None: return` instead of bare `next()`.

### 9.2 Stale appliance-list aliasing between `Hon` and `MQTTClient` — Low (latent)
[`connection/mqtt.py:20-25`](../custom_components/hon/pyhon/connection/mqtt.py#L20-L25):
```python
def __init__(self, hon: "Hon", mobile_id: str) -> None:
    ...
    self._appliances = hon.appliances
```
This captures a reference to the *list object* `Hon._appliances` at `MQTTClient` construction time. It works correctly today because `Hon.setup()` mutates that same list in place (`self._appliances.append(appliance)` in [`hon.py:101`](../custom_components/hon/pyhon/hon.py#L101)) and nothing in this codebase currently calls the `Hon.appliances` *setter* ([`hon.py:84-86`](../custom_components/hon/pyhon/hon.py#L84-L86)), which would rebind `Hon._appliances` to a new list object that `MQTTClient._appliances` would not see. Flagging as a latent/fragile-by-design issue rather than a live bug: any future code path that calls `hon.appliances = [...]` (e.g. a "reload appliances" feature) would silently desync the MQTT client's view of known devices, feeding directly into the `StopIteration` risk in 9.1.

**Suggested fix:** have `MQTTClient` read `self._hon.appliances` live (a property lookup) instead of caching the list reference, or expose an explicit `MQTTClient.refresh_appliances()` that's called if `Hon.appliances` is ever reassigned.

## 10. Robustness against partial/failed appliance loads

### 10.1 A partially-failed appliance is still added to the appliance list — Medium
[`hon.py:88-101`](../custom_components/hon/pyhon/hon.py#L88-L101):
```python
async def _create_appliance(
    self, appliance_data: Dict[str, Any], api: HonAPI, zone: int = 0
) -> None:
    appliance = HonAppliance(api, appliance_data, zone=zone)
    if appliance.mac_address == "":
        return
    try:
        await appliance.load_commands()
        await appliance.load_attributes()
        await appliance.load_statistics()
    except (KeyError, ValueError, IndexError) as error:
        _LOGGER.exception(error)
        _LOGGER.error("Device data - %s", appliance_data)
    self._appliances.append(appliance)
```
`self._appliances.append(appliance)` sits *outside and after* the `try`/`except` — so even when `load_commands()`/`load_attributes()`/`load_statistics()` fails partway (caught here) or fails with an exception type not in `(KeyError, ValueError, IndexError)` (e.g. `aiohttp.ClientError`, `TimeoutError`, `ApiError` — which per 7.1/7.2 is entirely possible, and which would propagate out of `_create_appliance` uncaught since only those three types are handled), the appliance either gets added in a half-initialized state (no commands, no attributes) or the whole `Hon.setup()` call aborts partway with some appliances loaded and others not.

A half-initialized appliance (empty `commands`, empty `available_settings`) reaching the HA integration layer is exactly the scenario that produces several of Part 1's findings (unguarded `self._device.settings[key]` lookups in `climate.py`/`switch.py`/`number.py` raising `KeyError`) — this is the most likely real-world trigger for those.

**Suggested fix:** only append the appliance if loading succeeded, or add an explicit `appliance.load_failed = True` flag the HA integration can check before creating entities for it; and broaden the caught exception types to include the network/API exceptions that `load_commands`/`load_attributes`/`load_statistics` can actually raise (per 7.1–7.3), so a single unreachable device doesn't abort loading the rest of the account's appliances.

## 11. Dependency risk

- `awscrt`/`awsiot` (via the `awsiotsdk` dependency, used for the MQTT push connection in `connection/mqtt.py`) ships without type stubs or a `py.typed` marker — confirmed by `mypy`, which reports `Skipping analyzing "awscrt": module is installed, but missing library stubs`. This was suppressed with a `[mypy-awscrt.*] ignore_missing_imports = True` override added to [mypy.ini](../mypy.ini) as part of the vendoring change, but it does mean this dependency's interface (callback signatures, exception types raised by `mqtt5_client_builder`/`client.subscribe(...).result(10)`, etc.) is entirely unchecked by tooling — another reason the exception paths flagged in 8.1/9.1 are easy to get wrong and hard to catch via static analysis.
- As with Part 1, there is no test suite covering any of this — the timeout gap (7.1), the narrow `except` in `send_parameters` (7.2), and the unguarded MQTT callback (9.1) would all be straightforward to regression-test (e.g. mock `aiohttp` to raise `TimeoutError` and assert a typed exception comes back) but nothing currently does.

## 12. Device/client identification constants sent to the hOn cloud — High (reliability), and worth noting given this repo's history

[`const.py:11-16`](../custom_components/hon/pyhon/const.py#L11-L16):
```python
APP_VERSION = "2.6.5"
OS_VERSION = 999
OS = "android"
DEVICE_MODEL = "pyhOn"
USER_AGENT = "Chrome/999.999.999.999"
MOBILE_ID = "pyhOn"
```
These aren't cosmetic — they're sent on **every single request** this library makes to Haier's backend: `USER_AGENT` goes into the `user-agent` header on every HTTP call ([`connection/handler/base.py:19`](../custom_components/hon/pyhon/connection/handler/base.py#L19), [`connection/handler/auth.py:17`](../custom_components/hon/pyhon/connection/handler/auth.py#L17), [`connection/auth.py:148`](../custom_components/hon/pyhon/connection/auth.py#L148)), and `APP_VERSION`/`OS_VERSION`/`OS`/`DEVICE_MODEL`/`MOBILE_ID` go into the device-identification payload sent with every command (`HonDevice.get()`, [`connection/device.py:34-44`](../custom_components/hon/pyhon/connection/device.py#L34-L44)) and into query parameters on `load_commands`/`app_config` ([`connection/api.py:100-101,253-254`](../custom_components/hon/pyhon/connection/api.py#L100-L101)).

None of these look like values that ever came from a real device:
- `OS_VERSION = 999` — not a real Android OS version (current Android versions are in the low-to-mid teens/twenties as of 2026); `999` reads as a placeholder that was never replaced.
- `USER_AGENT = "Chrome/999.999.999.999"` — not a well-formed Chrome UA string at all (a real one looks like `Mozilla/5.0 (Linux; Android 14; ...) ... Chrome/120.0.0.0 ...`) and the `999.999.999.999` version number doesn't correspond to any Chrome release that has ever shipped.
- `DEVICE_MODEL = "pyhOn"` and `MOBILE_ID = "pyhOn"` — these openly self-identify the traffic as coming from this library, rather than from Haier's own iOS/Android hOn app.

**Two distinct concerns:**
1. **Reliability.** If Haier's backend ever adds server-side validation on these fields (a plausible, low-effort move for any API operator — checking that `osVersion`/`appVersion`/user-agent look like a real, current device/app combination), requests using these values could start being rejected outright, breaking authentication and every command for every user of this integration simultaneously, with no client-side warning beyond an opaque API error at whatever endpoint first gets tightened.
2. **Fingerprinting / detection risk.** Because `DEVICE_MODEL`/`MOBILE_ID` literally spell out `"pyhOn"`, any request made by this library (or by extension, this integration) is trivially distinguishable server-side from genuine hOn app traffic — no reverse-engineering required, just a `WHERE deviceModel = 'pyhOn'` query. This repo already has a documented history of a takedown request from Haier over exactly this category of concern (see [takedown_faq.md](../takedown_faq.md) and [takedown_timeline.md](../takedown_timeline.md)); self-identifying, implausible client metadata makes it easier, not harder, for Haier to detect, rate-limit, or selectively block this traffic if they choose to, independent of the legal questions already documented there.

**Suggested fix:** at minimum, set `OS_VERSION` and `USER_AGENT` to values that correspond to a real, current Android/Chrome release (matching whatever `APP_VERSION` claims to be), so requests are indistinguishable from genuine hOn app traffic on these fields — this is a reliability hardening, not just a cosmetic one, since it reduces the chance of a server-side validation change breaking every user at once. Whether to also change `DEVICE_MODEL`/`MOBILE_ID` away from a self-identifying string is more of a project/policy decision than a pure code fix — worth a deliberate choice by whoever maintains this fork rather than a silent change, given the history in `takedown_faq.md`.

# Part 3: Proposed restructuring for readability & maintainability

Everything above is about *behavior* — bugs, missing error handling, reliability gaps. This section is about *shape*: today, most of the size and reading difficulty in `custom_components/hon/` comes not from complex logic but from large, declarative, per-appliance-type data tables sitting inline in the same files as the code that acts on them. Splitting data from behavior is the single highest-leverage structural change available here, and it's a mechanical, low-risk refactor — no behavior changes, just file moves and import updates.

## 13. Where the size actually comes from

Measuring where each platform file's line count actually goes (everything before its `async_setup_entry` function is entity-description dataclasses + the big per-appliance-type dict literal; everything after is the setup dispatcher + entity classes with real logic):

| File | Total lines | Description data (dataclasses + dict) | Behavior (setup + entity classes) | Data share |
|---|---|---|---|---|
| `sensor.py` | 877 | ~810 | ~67 | 92% |
| `binary_sensor.py` | 349 | ~319 | ~30 | 91% |
| `switch.py` | 559 | ~405 | ~154 | 72% |
| `select.py` | 337 | ~213 | ~124 | 63% |
| `number.py` | 327 | ~209 | ~118 | 64% |
| `climate.py` | 426 | ~106 | ~320 | 25% |
| `light.py` | 145 | ~55 | ~90 | 38% |
| `fan.py` | 132 | ~38 | ~94 | 29% |
| `button.py` | 132 | ~58 | ~74 | 44% |
| `lock.py` | 86 | ~28 | ~58 | 33% |

The four biggest files (`sensor.py`, `binary_sensor.py`, `switch.py`, `select.py` — 2,122 of the integration's 3,823 total lines, 55%) are 60–92% pure data. `const.py` (296 lines) is similar: it mixes true cross-cutting constants (`DOMAIN`, `PLATFORMS`, `APPLIANCES`) with 15 appliance-specific numeric-to-string lookup tables (`WASHING_PR_PHASE`, `MACH_MODE`, `AC_MACH_MODE`, `STAIN_TYPES`, etc.) that, per `grep`, are each used from exactly one place: `WASHING_PR_PHASE`/`MACH_MODE`/`DIRTY_LEVEL`/`STEAM_LEVEL`/`DISHWASHER_PR_PHASE`/`TUMBLE_DRYER_*`/`AP_*`/`REF_HUMIDITY_LEVELS`/`STAIN_TYPES`/`AC_POSITION_*` are only referenced from `select.py`/`sensor.py` description tables, and `HON_HVAC_MODE`/`HON_HVAC_PROGRAM`/`HON_FAN` are only referenced from `climate.py`'s entity logic. None of these lookup tables need to live in a shared `const.py` at all — they belong next to the one file that uses each of them.

## 14. Home Assistant's one hard constraint on this refactor

Home Assistant discovers entity platforms by convention: `hass.config_entries.async_forward_entry_setups(entry, PLATFORMS)` imports `custom_components.hon.<platform>` directly (e.g. `custom_components.hon.switch`) for each string in `PLATFORMS` ([`const.py:13-24`](../custom_components/hon/const.py#L13-L24)). **The ten platform files (`sensor.py`, `switch.py`, `binary_sensor.py`, etc.) must stay directly under `custom_components/hon/`** — they cannot be moved into a subpackage, or HA's platform loader will fail to find them. This rules out a "move everything into `platforms/`" restructure. It does not, however, constrain where a platform file's *data* lives — only the module HA imports by convention needs to be at the top level; that module is free to `import` a dict from anywhere else in the package.

- Each `descriptions/<platform>.py` file directly answers "what does the `TD` (tumble dryer) sensor look like" without also showing you `HonSensorEntity.async_added_to_hass` or unrelated appliance types' logic.
- No behavior changes anywhere — this is purely moving dataclass/dict definitions into new files and updating imports at the top of the ten platform files. Verifiable by diffing that no lines outside `import`/dataclass-relocation change, and by black/mypy passing identically before and after (already exercised in this session's vendoring work).

## 16. The vendored `pyhon/` library needs no comparable reshuffle

Unlike the integration layer, `pyhon/`'s existing structure already separates concerns reasonably well — `connection/` (transport + auth), `parameter/` (the settings type hierarchy), `appliances/` (per-type extra behavior), and flat top-level modules for the rest (`hon.py` facade, `appliance.py`, `commands.py`, `command_loader.py`, `exceptions.py`, etc.). None of its files are dominated by inline data tables the way the integration's platform files are — its data (parameter definitions, appliance capabilities) comes from the hOn API at runtime, not from source-level constant tables, so there's no equivalent "data vs. behavior" split to make.

The only structural note worth recording: the fixes recommended in Part 2 (§7.3's new `HonConnectionError` in `exceptions.py`, §7.1's timeout config in `connection/handler/base.py`, §8.1's `try/except` in `connection/mqtt.py`) all fit into existing files in their existing locations — implementing the Part 2 fixes and doing the Part 3 restructuring are independent, can land in either order, and don't conflict.

## 17. Suggested migration order

Since this is a pure refactor (no behavior change), it's safe to do independently of and either before or after the bug fixes in Parts 1–2. Suggested order, each step independently shippable and verifiable with `black --check` + `mypy -p custom_components.hon` + a manual HA reload:

1. Create `descriptions/__init__.py` and move one platform at a time, smallest first to prove the pattern before tackling the big ones: `lock.py` → `descriptions/lock.py`, then `fan.py`, `button.py`, `light.py`, `number.py`, `select.py`, then the three big ones `switch.py`, `binary_sensor.py`, `sensor.py`.
2. For each platform: cut the entity-description dataclass(es) and the top-level dict (e.g. `SWITCHES`) into `descriptions/<platform>.py`; leave `import` of that dict plus everything from `async_setup_entry` onward in the original file.
3. Once all ten are moved, trim `const.py` down to `DOMAIN`/`MOBILE_ID`/`CONF_REFRESH_TOKEN`/`PLATFORMS`/`APPLIANCES`/`LANGUAGES`, relocating each lookup table to the one `descriptions/<platform>.py` (or, for `HON_HVAC_MODE`/`HON_HVAC_PROGRAM`/`HON_FAN`, directly into `climate.py`) that actually uses it.
4. Extract the coordinator wiring from `__init__.py` into `coordinator.py` (this step pairs naturally with implementing the audit's fallback-poll fix, #3/8.2, in the same place).
5. Re-run `black`, `mypy -p custom_components.hon`, `flake8`, and a manual reload against a real (or `TestAPI`/`hon-test-data`) account to confirm no entities were dropped or renamed — a diff of the HA entity registry before/after is the cheapest way to catch a missed `unique_id` or description during the move.
